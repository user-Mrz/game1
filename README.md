# 兵临城下 · 水墨策略战棋

一款运行在手机浏览器里的回合制策略战棋游戏。黑白水墨风，HTML5 Canvas 渲染，触摸操作，无需安装。

你扮演一方诸侯，在随机生成的山河间建城、屯田、征兵，与最多 9 名 AI 诸侯争夺天下。**摧毁所有敌方主营（「帅」字大印）即获胜**；自己的主营被攻破，则全盘皆输。

## 一、这游戏在玩什么

它不是「攒资源、爆兵、A 过去」的快餐 RTS，核心是**补给线**。

游戏里只有一种资源——**粮草**。粮草不是钱，是油：每个兵种自带储备，储备决定了它能走多远。

> 步兵单程能走 22 格，轻骑兵 40 格，重骑兵 28 格。

**粮草断了，兵是真的会垮**：

| 剩余续航 | 战力系数 |
|---|---|
| ≥ 6 回合 | ×1.00 满战力 |
| 3 ~ 6 回合 | ×0.85 缺粮 |
| 1 ~ 3 回合 | ×0.65 断粮在即 |
| < 1 回合 | ×0.45 正在掉兵 |

储备耗尽后，每缺 1 点粮掉 1 点血，掉光整队消失。所以一场仗打赢打不赢，往往在你出兵前就决定了——**这一趟，粮够不够走回来**。

这也决定了战场节奏：步兵/弓兵只有 22 格作战半径，而两家主营相距约 20 格。兵出得去，未必回得来。真正的胜负手在**农田、粮仓和后勤补给兵**上，而不是在兵力数字上。

## 二、兵种

五种兵种互相克制，没有一种能通吃全场，**混编才有解**。

| 兵种 | 攻击 | 血量 | 移动 | 射程 | 造价 | 定位 |
|---|---|---|---|---|---|---|
| **步兵** | 500 | 1000 | 1 | 1 | 2300 | 占线基石，最便宜的战力，负责吸收伤害 |
| **弓兵** | 385 | 550 | 1 | 2 | 1500 | 后排火力，移动当回合射程降为 1，需步兵掩护 |
| **轻骑兵** | 450 | 600 | 4 | 1 | 1900 | 高速袭扰，切弓兵与后勤兵、断粮道，正面打不过步兵 |
| **重骑兵** | 800 | 1200 | 2 | 1 | 3500 | 唯一破阵单位，一击可秒轻骑/弓兵/补给兵，粮耗最高 |
| **后勤补给兵** | 0 | 300 | 1 | — | 800 | 无攻击，自身不耗粮，给相邻友军补储备 |

**关键规则**：单位攻击是「兵力对撞」——攻击力即伤害，剩余兵力即血条。部队被打残后不会恢复，只能靠补给兵或粮仓补储备，或回城重造。

## 三、建筑

共 11 种，围绕「产粮 → 出兵 → 防守」三层展开。

**核心**

- **主营** — 12000 血，被摧毁即失败。摧毁敌方主营后，其所有建筑与单位归你所有

**经济**

- **农田** — 2400 粮草，平原产 900/回合，**沃土翻倍到 1800**。一块农田大约供养一个步兵
- **粮仓** — 1200 粮草，单位站上去按 1 粮草换 5 储备补满。补满一个满编步兵约需 4400 粮，是重建价的 1.9 倍

**军事**

- **兵营** ×5（步兵营 / 弓兵营 / 轻骑兵营 / 重骑兵营 / 后勤补给兵营）— 兵营价 = 兵种价，生产后需冷却 1~4 回合
- **箭塔** — 2800 粮草，3000 血，每回合对 2 格内敌军造成 400 伤害。3 回合可点杀一个步兵，而步兵要砍 6 刀才能拆掉它——单兵强攻箭塔必亏
- **城墙** — 700 粮草，3000 血，不能攻击，纯换时间
- **哨塔** — 800 粮草，8 格视野，全游戏最强的眼睛

## 四、地形与战争迷雾

五种地形随机生成：

- **平原** — 通行无阻
- **沃土** — 农田产出翻倍，兵家必争
- **森林** — **单位进入森林后对敌方隐身**，除非敌人贴身进林或林内单位先开火
- **山地** — 完全无法通行
- **河流** — 进入后本回合无法继续移动

**战争迷雾**是这游戏最折磨人的部分：兵种视野 = **移动力 × 3**（步兵 3 格、轻骑兵 12 格、重骑兵 6 格），普通建筑只有周围 1 格的 9 宫格，哨塔独一档 8 格。森林、山地、河流把地图切得支离破碎，你的情报全靠**哨塔和轻骑兵的机动**。看不见的敌人，往往就在下一格。

已探索过的区域会留下灰色地形轮廓，但离开视野后只能看到自己的建筑——敌人去哪了，得靠你自己推。

## 五、建造范围

建筑不是想盖就盖。落地必须同时满足两个条件：

1. 落在己方**建造视野**内（只由兵种提供，建筑和哨塔一律不给）
2. 落在以主营为中心的**建造半径**内（每回合 +1 格，与步兵移动力同步）

这条规则的用意很直接：**扩张速度不许跑在部队前面**。你不能靠「建一座塔 → 塔开出新范围 → 再建一座」一路滚到对面家。

## 六、对局设置

| 选项 | 可选值 |
|---|---|
| 地图大小 | 50×50（快节奏，约 10 回合接敌）/ 70×70（标准，15~20 回合）/ 85×85（长局，30 回合后接敌） |
| AI 对手 | 1 ~ 9 名 |
| 难度 | 简单 / 普通 / 困难 / 极难 |

难度会同时改变 AI 的**智能程度**与**属性倍率**：简单难度下 AI 不懂后勤、不会远程攻击；困难以上 AI 会主动拆你的主营、智能选敌、残血撤退。极难难度 AI 血量 +50%、攻击 +25%，还额外带 4000 起始粮草。

## 七、操作

手机上全程触摸：点击选中、点格子移动/攻击、双指缩放、拖动平移。

桌面端支持自定义快捷键（默认值，可在「快捷键设置」里改）：

| 操作 | 按键 |
|---|---|
| 结束回合 | `E` |
| 建造菜单 | `U` |
| 大地图 | `M` |
| 放大 / 缩小 / 重置 | `+` / `-` / `0` |
| 平移视角 | 方向键 |

游戏内置**新手教学**，首次进入建议先过一遍——补给规则不讲清楚，前两局很容易莫名其妙地崩盘。

## 八、技术实现

前后端分离。前端负责渲染与交互，后端负责重活。

```
┌─────────────────────┐        ┌──────────────────────┐
│   Vue 3 + Vite      │  HTTP  │  Spring Boot 3.5     │
│   Canvas 渲染       │ <────> │  Java 21 / Maven     │
│   触摸交互          │  /api  │  SQLite (JPA)        │
└─────────────────────┘        └──────────────────────┘
       手机浏览器                       地形 / AI / 存档
```

**为什么后端要算 AI**：大图 + 9 个 AI 时，前端跑完整回合结算会让浏览器内存飙升、卡顿明显。把 AI 行动迁移到后端后，前端只保留人类玩家的视野数组（`Uint8Array`），大地图下内存占用显著下降。

**地形也不在前端**：地形数据由后端 `MapService` 生成并存储，前端按需拉取，避免每回合来回传输几十万格的地形数组。

### 技术栈

- **前端**：Vue 3.5 Composition API · Vite 6 · HTML5 Canvas 2D
- **后端**：Spring Boot 3.5.16 · Java 21 · Spring Web · Spring Data JPA
- **数据库**：SQLite（`sqlite-jdbc` + `hibernate-community-dialects`），另附 MySQL 8.0 建库脚本
- **构建**：Maven · npm

### 目录结构

```
.
├── src/                     前端源码
│   ├── game/                核心逻辑（AI、战斗、经济、视野、寻路、渲染）
│   ├── components/          Vue 组件（主界面、HUD、建造菜单、教学等）
│   ├── composables/         useGame / useSettings / useDraggableCard
│   └── api/                 后端接口客户端
├── backend/                 Spring Boot 后端
│   └── src/main/java/com/inkgame/backend/
│       ├── map/             地形生成与分发
│       ├── sim/             AI 回合结算引擎
│       └── save/            存档 / 读档
├── database/                数据库初始化脚本（SQLite / MySQL）
├── public/                  静态资源
├── 美术素材/                 美术原稿
└── 玩法设计.txt              玩法设计文档
```

## 九、本地运行

### 环境要求

- Node.js 18+
- JDK 21
- Maven 3.9+

### 1. 启动后端

```bash
cd backend
mvn spring-boot:run
```

服务监听 `http://localhost:8080`。数据库为 SQLite，首次启动时 JPA 会自动建表并在 `backend/data/` 下生成 `game.db`，**无需手动初始化**。

> 如需改用 MySQL，执行 [database/init.sql](database/init.sql) 建库建表，并把 `backend/src/main/resources/application.yml` 的数据源改为 MySQL 连接。

### 2. 启动前端

```bash
npm install
npm run dev
```

Vite 已配置代理，前端 `/api/*` 请求自动转发到 `localhost:8080`。控制台会给出局域网地址，**手机与电脑连同一个 Wi-Fi 即可直接扫码试玩**（`server.host` 已开启）。

### 3. 生产构建

```bash
npm run build
```

产物在 `dist/`。部署时需把 `/api` 反向代理到后端 8080 端口，或在构建时指定后端地址：

```bash
VITE_API_BASE=http://your-host:8080/api npm run build
```

## 十一、设计上的几个取舍

写在这里，是因为这些数字不是拍脑袋定的：

- **为什么补给上限按「射程」算，而不是「回合数」**：如果所有兵种都按固定回合数给储备，作战半径就会退化成移动力的正比——步兵永远走不到对面，前线只能堆在自家门口互相看着。改成「单程 16 格 + 抵达后 6 个战斗回合」反推，步兵才有 22 格的实际活动范围。
- **为什么「饥兵」用剩余回合数而不是储备百分比**：各兵种储备上限差 5 倍，同样 50% 储备，步兵还剩 11 回合、轻骑只剩 5 回合。百分比在不同兵种间不可比，回合数可比。
- **为什么粮草兑换率全局只有一个数**：储备可以被补给兵 1:1 转给任意友军，等于一种完全流通的商品。只要两个兵种汇率不同，就存在无风险套利——在便宜的兵种上买储备，转手补给贵兵种。实测按兵种取不同汇率时，后勤系统会直接崩掉。
- **为什么建筑不给建造视野**：否则「建塔 → 开新范围 → 再建塔」会自我滚动，一路滚到对面家门口。
